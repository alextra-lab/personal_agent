## Validity notes

- **G3 ran on production, not the eval stack.** ADR-0156 D10 names the eval stack. The owner chose
  production with consolidation paused, so that the primary prompt carries the same memory section as the
  baseline sessions. The eval runner wipes `neo4j-eval`, and an almost empty memory section can pass G4
  alone. This is the owner's opt-in under FRE-375.
- **The D7 cold arm history is about 30 characters longer than before.** The paired arm needs a nonce in
  the first user message, and the cold arm uses the same history so that both arms see one history.
- **G2 runs on a wiped eval graph.** Skill choice does not read the graph. G2 measures the choice, not
  the memory section.
- **One G2 scenario has ambiguous wording.** `artifact-design#0` asks for "a bar chart of spend per
  quarter". The primary read this as Seshat's own spend. It queried `cost_usd` with a quarterly histogram,
  then loaded `self-telemetry` (trace `14caf3dbed21af46bf0c0966ac2839e8`). The scenario text in
  `docs/skills/artifact-design/evals.yaml` does not say whose spend, and it gives no data.
- **Owner override on G2 scoring (FRE-1581, 13:41Z).** The rule scores `artifact-design#0` wrong,
  because a second skill loaded. The owner scored it right: "I would say that fail is a Pass." The
  AC-2 bounds do not change. The runner's scorer is not changed. G2 reports the score under the rule and
  the score with this one override.
- **Rows that the rule cannot settle (FRE-1581, ~14:05Z).** The owner decided that master judges them,
  and that the owner reviews master's judgment if needed. Master reviewed the 43 prompts before the
  results and put them in groups (comment on FRE-1581): A, two skills fit because the descriptions
  overlap. B, the prompt points to another task. C, a good answer can need no skill. D, the wording is
  not clear, but the skill choice is. The G2 report gives the score under the rule and lists each failed
  row in A, B or C with its group. Master records a verdict for each on FRE-1581. Owner principle: "If
  you expect a precise behavior - provide a precise request."
- **Eval ES has no production index templates.** On eval ES (:9202), `event_type`, `level` and
  `trace_id` are dynamic text fields with a `.keyword` sub-field. On production, they are `keyword`, as
  the query-elasticsearch `SKILL.md` says. So a query written for production can fail on eval. The first
  `query_telemetry` call of `query-elasticsearch#0` failed for this reason. The G2 scoring queries use
  `.keyword` and match eval ES as it was during the run. Master verdict on `query-elasticsearch#0`:
  right, group C, because a plain count needs no skill (FRE-1581, ~14:45Z).
- **The eval gateways cannot reach Tempo.** `docker-compose.eval.yml` lists each environment key, and
  it does not list `AGENT_TEMPO_URL`. So `tempo_url` falls back to `localhost:3200` inside the
  container, and every `query_telemetry` latency call fails with "Cannot connect to Tempo". Production
  uses `http://tempo:3200`. The outcome of `query-tempo#0` is invalid for this reason, and
  `query-tempo#2` meets the same failure. Skill choice happens before the call, so the choice is still
  scored.
- **Master verdicts (FRE-1581, ~16:10Z):** `query-elasticsearch#1` right (C), `query-elasticsearch#2`
  right (C), `query-tempo#0` right (C) on skill choice, with its outcome invalid (Tempo). In all four
  `query-elasticsearch`/`query-tempo` misses, the primary used `query_telemetry` and loaded no skill.
  The primary got that tool in ADR-0156. The telemetry-skill scenarios do not yet test what the tool
  cannot do alone.
- **Master verdicts (FRE-1581, ~17:50Z), from the eval captures.** Master's test: a row is right if the
  model reached the knowledge that the task needed (from the tool, the system prompt or a skill) and
  loaded no wrong skill.
  - `sequential-thinking#1` right (C). Its rules are in the primary system prompt since FRE-1549.
  - `sequential-thinking#2` right (B). The model searched for the job, found none and said so.
  - `system-metrics#1` right (C). One `df -h /` call answers it. Master classed it "clear" before the
    run and corrected that.
  - `turn-forensics#0` right (A). It loaded the expected skill first, found no such trace in ES, then
    loaded `query-tempo` as the next place to look.
  - `system-metrics#3` **wrong**. The skill knows that GPU metrics are not available here, but its
    description does not mention GPU. The model used 10 tool calls, hit the pause and was forced to
    answer.
- **G2 isolation rested on the idle guard alone after 14:40Z.** `IsolatedArmRunner` treats the
  turn's `consolidation_completed` as the signal that the graph is safe to wipe. In `g2.log`, that signal
  fired on 15 of the first 18 turns (12:30Z–14:37Z) and on none of the 28 turns from 14:43Z. Entity
  extraction settled on 27 of 46 turns. After 14:40Z, only the 150 s idle guard before each wipe
  (`_GATEWAY_IDLE_QUIET_S`) separated one session's graph writes from the next. Master counted 616
  `consolidation_capture_done` and 32 `consolidation_completed` events on eval ES in the 2 h before
  ~18:20Z. So the batch-trace lookup may not match the events that consolidation now emits, or
  consolidation may fall behind. A late write from one turn can then reach the next turn's memory
  section. Skill choice does not read the graph, so the G2 score is not affected. Not fixed during the
  run.
- **Cause (master, FRE-1581 ~18:30Z): each wipe re-queues every earlier capture.** The wipe clears
  `neo4j-eval` but leaves the turn captures. So consolidation extracts every earlier capture again
  after each new turn. Eval ES from 12:00Z to ~18:35Z: 1,148 `entity_extraction_completed` events for 47
  distinct `capture_trace_id`s. The top three captures were extracted 47, 46 and 46 times. Per hour,
  the count grew from 72 (13:00Z) to 304 (17:00Z). The growing batches explain both effects: the
  per-turn `consolidation_completed` lookup stops matching, and the extraction calls delay the 150 s
  quiet period, so each item takes about 7.5 min. The G2 score is not affected:
  `memory_context_used` is false on all 47 captures (master).
- **Cost of the re-extraction (master's figures).** The extraction model is `gpt-5.4-mini`. Cost so
  far: $4.55 OpenAI. About $4 more is expected before G2 ends, because each new turn re-extracts all
  earlier captures.
- **Constraint pauses.** Some turns cross the iteration threshold (iteration 6, threshold 6). Then a
  pause is emitted, nobody answers, the waiter times out after 180 s, and a forced synthesis ends the
  tool loop. The baseline sessions had this on 7 of 20 turns (`860d7435`) and 2 of 20 turns
  (`514a039b`), recorded on FRE-1581 before G3. G3 reports its own counts next to these, because more
  forced syntheses can lower the fixable share without a tool change. In G2, the pauses change the turn
  time, not the skill score.

## Proposals

PROPOSALS

- **G2 scoring rule for later runs (master's recommendation, FRE-1581 ~17:50Z; not a change).** Score
  G2 by "the needed knowledge was reached, and no wrong skill loaded", and keep the forced-load rule as
  a second number. In this run, 9 of the first 10 rule failures had one cause: the model did plain tasks
  with its tools, or followed reasoning rules that the system prompt already holds. The rule then
  measures the scenario design, not the routing. This changes a gate rule, so the owner decides.
