# FRE-1692: Scaleway models fail every turn: litellm refuses tools for scaleway/glm-5.3 and scaleway/deepseek-v4.1-flash

The owner's first live turn on glm-5.3-scaleway failed at once, twice.

## Defect

litellm refuses the call before any request is sent:
"litellm.UnsupportedParamsError: scaleway does not support parameters: ['tools'], for model=glm-5.3."
litellm's built-in scaleway provider table does not list tools for glm-5.3 or for deepseek-v4.1-flash. `litellm.get_supported_openai_params(model, custom_llm_provider="scaleway")` has no "tools" for either model. The models do handle tools: a direct probe got a correct tool call from both. The earlier PR's tests replaced the transport, so they never reached litellm's parameter check.

Every primary turn sends tools, so both Scaleway models fail on every turn today.

## Fix (you choose, and state the reason)

- Dispatch scaleway the way slm_local is dispatched: litellm's OpenAI-compatible provider (openai/{model_id}) with the catalog base_url. Or
- keep the scaleway/ provider and pass allowed_openai_params for the parameters that the catalog declares (tools, tool_choice, reasoning_effort).

Whichever is chosen, the egress guard and the cost ledger row with provider scaleway must stay as they are.

## Acceptance criteria

- AC-1: a test that goes through litellm's real parameter check (litellm.completion's validation is not mocked, only the HTTP transport) sends a scaleway request with tools for each of the two models. Fails on the current code with UnsupportedParamsError.
- AC-2: the existing scaleway tests stay green: guarded client, Bearer secret, cost row with provider scaleway and the priced cost.
